## Current System

**Product:** 10xCards — web app (Astro SSR + React islands, Supabase, Cloudflare Workers).

**Sets today:** Logged-in user creates named flashcard sets on `/dashboard` (POST `/api/flashcard-sets/create`), lists them sorted by `updated_at`, opens `/sets/<id>` for card CRUD, AI save, and SRS review (`/sets/<id>/review`).

**Database:** `flashcard_sets` has RLS policies for `select`, `insert`, `update`, and `delete` owned rows; `flashcards` references sets with `ON DELETE CASCADE`. Application layer exposes create + list only — no update-name or delete-set API/UI.

**Users:** Individual learners with email/password accounts; flat role model; sets are private per owner.

## Vision & Problem Statement

**Delta:** Użytkownik może tworzyć zestawy i zarządzać fiszkami wewnątrz zestawu, ale nie może poprawić nazwy zestawu ani usunąć zestawu, który jest pusty lub zawiera fiszki. Błędne lub zbędne zestawy zostają na liście bez możliwości uporządkowania — to tarcie w codziennym workflow (np. literówka w nazwie, testowy zestaw po sesji AI).

**Insight:** Warstwa danych i RLS już przewidują `UPDATE`/`DELETE` na `flashcard_sets`; brakuje tylko ekspozycji w API i UI — to niska złożoność techniczna przy wysokiej wartości UX.

## User & Persona

**Persona (bez zmian):** Indywidualny learner — student, profesjonalista, samouk.

**Moment:** Na `/dashboard` przegląda listę zestawów i chce szybko poprawić nazwę albo usunąć zestaw, którego już nie potrzebuje — bez obejść (pusta nazwa, zostawianie „śmieciowych” zestawów).

**Koszt dziś:** Brak edycji nazwy i usuwania zestawu; użytkownik utknął z nieaktualnymi lub testowymi zestawami na liście.

## Access Control

**Obecny model:** Rejestracja i logowanie email + hasło. Model płaski — każdy użytkownik zarządza wyłącznie własnymi zestawami. Zestawy są prywatne (RLS: `user_id = auth.uid()`).

**Zmiana w tym slice:** Brak zmian w auth i rolach. Nowe operacje (zmiana nazwy, usunięcie zestawu) podlegają tym samym politykom RLS co istniejące `update`/`delete` na `flashcard_sets`.

## Success Criteria

### Primary

- Zalogowany użytkownik może z `/dashboard` usunąć niechciany zestaw (pusty lub z fiszkami) oraz poprawić mylącą nazwę innego zestawu — obie operacje działają end-to-end bez obejść.

### Secondary

- Przy usuwaniu niepustego zestawu użytkownik widzi w potwierdzeniu liczbę fiszek, które zostaną usunięte; pusty zestaw znika po jednej akcji bez dodatkowego kroku.

### Guardrails

- Tylko właściciel zestawu może go edytować lub usunąć — bez regresji RLS (inny użytkownik nie ma dostępu do cudzych zestawów).

## User Stories

### US-01: User removes an unwanted set and fixes a misleading set name from the dashboard

- **Given** a logged-in user on `/dashboard` with at least two flashcard sets
- **When** they delete a set they no longer want (confirming in the modal if it contains cards) and edit another set’s name to fix a typo or misleading title
- **Then** the deleted set no longer appears in the list, the renamed set shows the new name, and opening `/sets/<id>` for the renamed set still works

#### Acceptance Criteria

- Empty sets delete without confirmation; non-empty sets require confirmation showing card count
- Rename validates name length (same rules as create: 1–80 characters)
- Only the set owner can perform rename or delete (RLS)
- After delete, `/sets/<deleted-id>` is not reachable (redirect or not-found)

## Business Logic

No domain logic change. This slice is UI/API exposure of existing set lifecycle operations (update name, delete with cascade). SRS scheduling and AI extraction rules are unchanged.

## Constraints & Preserved Behavior

- **RLS:** Only the set owner can rename or delete; existing `flashcard_sets` policies apply without modification.
- **Data:** Deleting a set removes all child flashcards via existing `ON DELETE CASCADE`; no orphan cards.
- **Validation:** Renamed set names use the same rules as create (1–80 characters).
- **URLs:** `/sets/<id>` for a deleted set must not show stale data (redirect to dashboard or not-found).
- **Preserved flows:** Create/list sets on dashboard, card CRUD on set detail, SRS review, AI generator — no intentional behavior change beyond set rename/delete availability.
- **Backward compatibility:** No API contract changes for existing card or SRS endpoints.

## Non-Functional Requirements

- After a successful rename, the dashboard list shows the new set name without requiring a full app restart.
- Deleting a set removes all associated flashcards from storage; no orphaned cards remain queryable under that set.

## Non-Goals

- **No rename/delete on `/sets/<id>`** — set name edit and delete actions live on the dashboard list only in this slice.
- **No soft-delete / trash / restore** — delete is immediate with DB cascade.
- **No bulk delete** — one set at a time; no multi-select or “delete all empty sets.”
